# Swarms v17「InterLink」

InterLink 是一个月的工作成果：**2026 年 10 月 2 日至 11 月 2 日之间的 227 次提交**，涉及 271 个文件，**+15,729 / −13,395 行**。这是第一次在一个大版本中，`swarms/` 本身变小了：**+5,845 / −8,080**，在新增十一个模块的同时净删除了 2,235 行。`tests/` 增加了 +8,378 / −960，测试函数从 944 个增加到 1,130 个。

Zena（v14）让框架变得可观测。Akira（v15）让它变得诚实。Overclock（v16）让它可计量，而且更快。InterLink 让它**互联，而且精简**。

这个版本贯穿着五条主线。

第一条是**频道**，这也是这个版本名字的由来。过去，一个智能体的对话只存在于它自己的记忆里，别处都没有。现在任何 `Agent` 以及九个结构都可以接受一个 `channel=`：一个在运行之前读取此前说过的话、在运行之后发布自己所说内容的地方。一共提供六种频道：一个在智能体交谈时你可以打开查看的 Markdown 文件，一个可供消费者线程阻塞等待的队列，一张可以跨进程安全使用的 SQLite 表，一台远程 HTTP 服务器，你自己邮箱里的一个邮件会话，以及一个人们可以在邮件客户端里直接回复的 AgentMail 会话。在一个非空频道上的第二次运行，会从第一次停下的地方继续。

第二条是**启动速度**。`import swarms` 以前要 **1.91 秒**，现在只要 **0.28 秒**（在同一台机器上取九个全新进程的中位数，v16 对比 v17）。它不再加载 litellm、RouteHub、mcp、networkx、OpenTelemetry、starlette 或 sqlite3，直到真正有东西用到它们；它不往磁盘写任何东西；构建一个设置了各项上限的 `Agent` 也不会打开任何网络连接。安装 `swarms[fast]` 会让模型调用经由 RouteHub，这让每次调用的开销降低一半以上，峰值内存也从大约 220 MB 降到 100 MB。

第三条是**满宽度并发**。`ConcurrentWorkflow` 一次最多运行 32 个智能体，`GraphWorkflow` 按 CPU 核心数设定线程池大小，所以在一台 12 核的笔记本上，一个 100 节点的层要分 11 个一批地跑。现在两者默认都会让所有节点同时运行：一个 100 节点的扇出从 **2.04 秒降到 0.21 秒**，而 LangGraph 在同一张图上是 1.44 秒。

第四条是**交回答案**。在默认的 `output_type` 下，`Agent.run` 返回的是整段对话，而有七个结构和辅助函数把这个值当成了智能体的回复来用。`HeavySwarm` 在本该返回一个 24 个字符的答案时，返回了一段 382,000 个字符的对话记录。`ReflexionAgent` 把每一次迭代都嵌套进了下一次。`handoff_task`、`GKPAgent`、`ExpertPanelDiscussion` 和 `IterativeReflectiveExpansion` 也有同样的缺陷。现在它们都记录并返回答案本身。

第五条是**失败会抛出异常，以及更小的接口面**。`HeavySwarm`、`MixtureOfAgents`、`MajorityVoting`、`AuctionSwarm` 和 `AgentRearrange` 会返回一个错误字符串，或者把一个异常当作一张选票，所以 `SwarmRouter(fallback_swarms=...)` 从来没有真正回退过。现在它们会抛出异常。重试和回退从三层叠加收拢为一个扁平的循环。另外，四十多个什么也不做、或者做错了事的参数、方法、模块和类都被移除了：`SwarmRearrange`、`create_agents_from_yaml`、`BaseTool` 的一半、`multi_modal`、`sop`、`n`、`bulk_run`，以及其余这些。

这篇文章会把这些全部讲清楚。先讲新特性和改进，然后是整个版本**逐日、逐个提交**的完整记录。

```bash
# pip
pip install -U swarms

# with RouteHub and rustworkx, the two optional speedups
pip install -U "swarms[fast]"

# uv
uv pip install -U swarms

# uv, in a project managed by uv
uv add swarms --upgrade

# poetry
poetry add swarms@latest

# Docker: the official image, on Python 3.13
docker pull swarmscorp/swarms:latest
```

如果你需要可复现的安装，就固定版本：

```bash
pip install "swarms==17.0.0"
uv pip install "swarms==17.0.0"
```

确认你装到的版本：

```bash
python -c "import swarms; print(swarms.__version__)"
```

**如果你是从 v16 升级上来的，请先阅读[破坏性变更](#breaking-changes)一节。** 现在如果你不提供系统提示词，`Agent()` 就不发送任何系统提示词；工作流默认不再自动保存；失败的 swarm 会抛出异常，而不再返回一个错误字符串；一长串未使用的参数也被移除了。大多数被移除的关键字参数会被 `**kwargs` 吸收并被静默忽略，所以请对照那张表逐项检查，不要等着 `TypeError` 来提醒你。

## 新特性

### 通信频道：通过一个共享媒介读取和发布消息的智能体

**这是 InterLink 的头号能力。** `CommsChannel` 是一个地方，智能体在这里读取别人说过的话，并发布自己要说的话。它的接口只有两个方法，外加一个可选方法：

```python
class CommsChannel(ABC):
    def post(self, agent_name: str, content: str) -> None: ...  # append one message
    def messages(self) -> List[Dict[str, Any]]: ...            # [{"agent_name": ..., "content": ...}], oldest first
    def clear(self) -> None: ...                               # optional
```

一共提供六种实现，全部从 `swarms` 导出：

| 频道 | 对话存放在哪里 | 适合做什么 | PR |
|---|---|---|---|
| `FileChannel(path)` | 一个 `.md` 或 `.txt` 文件，每条消息一个 `## @name` 标题 | 实时观看智能体交谈，在两次运行之间编辑对话记录 | [#2826](https://github.com/kyegomez/swarms/pull/2826) |
| `QueueChannel(q=None)` | 进程内的历史记录加一个队列 | 一个在每条消息到达时阻塞等待的消费者线程；传入一个 `multiprocessing.Queue` 即可跨进程 | [#2826](https://github.com/kyegomez/swarms/pull/2826) |
| `SqliteChannel(path, name)` | SQLite 表中的行，一个文件里可以存放多段对话 | 线程安全、进程安全的共享状态，可以用 SQL 查询历史 | [#2826](https://github.com/kyegomez/swarms/pull/2826) |
| `HttpChannel(url, headers)` | 另一台服务器，通过 `GET` / `POST` / `DELETE` 访问 | 不同机器上的智能体共享同一段对话 | [#2908](https://github.com/kyegomez/swarms/pull/2908) |
| `SmtpChannel(...)` | 你自己邮箱里的一个邮件会话，通过 SMTP 和 IMAP 访问 | 人们在自己的邮件客户端里回复智能体 | [#3036](https://github.com/kyegomez/swarms/pull/3036) |
| `AgentMailChannel(inbox_id, to)` | 一个 AgentMail 收件箱里的邮件会话，通过它的 REST API 访问 | 同上，但不需要自己运行邮件服务器 | [#3034](https://github.com/kyegomez/swarms/pull/3034) |

把一个频道交给智能体，它就会在运行前把频道内容当作之前的对话轮次读入，把任务发布一次，并在一次成功运行之后，以它的 `agent_name` 发布最终答案。失败的运行不会发布任何内容。

```python
from swarms import Agent, FileChannel

channel = FileChannel("runs/ev_conversation.md")

researcher = Agent(
    agent_name="Researcher",
    system_prompt="You gather facts and figures. Answer in a short bullet list.",
    model_name="gpt-5.4",
    max_loops=1,
    channel=channel,
)
writer = Agent(
    agent_name="Writer",
    system_prompt="You turn the facts in the conversation into a short report.",
    model_name="gpt-5.4",
    max_loops=1,
    channel=channel,
)

task = "Report on the EV battery market."
researcher.run(task)
writer.run(task)   # the writer reads the researcher's answer as a prior turn

print(channel.path.read_text())
```

这个文件是纯 Markdown，所以你可以在运行进行的同时用编辑器打开它：

```markdown
## @Human

Report on the EV battery market.

## @Researcher

- Global demand grew 31% last year ...

## @Writer

The EV battery market ...
```

**结构也可以接受频道。** `SequentialWorkflow`、`AgentRearrange`、`ConcurrentWorkflow`、`GraphWorkflow`、`MixtureOfAgents`、`GroupChat`、`HierarchicalSwarm`、`PlannerWorkerSwarm` 和 `MajorityVoting` 都接受 `channel=`，并把它交给自己构建的 `Conversation`，包括它们为每个任务重新构建的那些。`SwarmRouter` 会把它转发给自己构建的任何 swarm。结构会解除其成员各自的频道（并给出一条警告），这样对话记录只会被写入一次；扇出则会按智能体顺序发布答案，而不是交错发布。

```python
from swarms import Agent, FileChannel, SequentialWorkflow

workflow = SequentialWorkflow(
    agents=[researcher, writer, reviewer],
    max_loops=1,
    channel=FileChannel("runs/sequential.md"),
)
workflow.run("Report on the EV battery market.")
```

**一个非空的频道会让运行继续下去。** 正是这项特性让文件频道不只是一份日志。手工编辑 `runs/sequential.md`，然后让一个新的结构指向它：

```python
editor = Agent(
    agent_name="Editor",
    system_prompt="Tighten the report in the conversation to half its length.",
    model_name="gpt-5.4",
    max_loops=1,
)

SequentialWorkflow(
    agents=[editor], max_loops=1, channel=FileChannel("runs/sequential.md")
).run("Shorten the report above.")
```

`GroupChat`、`HierarchicalSwarm` 和 `PlannerWorkerSwarm` 最初会在每次运行开始时清空自己的对话，这会把那段预置内容丢掉。现在它们改为从频道重建对话（[#2880](https://github.com/kyegomez/swarms/pull/2880)）。

**用 `QueueChannel` 在每条消息到达时以流式获取它。** 消费者在 `wait()` 上阻塞或者直接迭代，`close()` 会结束循环：

```python
import threading
from swarms import QueueChannel, SequentialWorkflow

channel = QueueChannel()
workflow = SequentialWorkflow(agents=[researcher, analyst, writer], channel=channel)

def produce():
    try:
        workflow.run("Report on the EV battery market.")
    finally:
        channel.close()

threading.Thread(target=produce, daemon=True).start()

for message in channel:   # blocks until the next post
    print(f"\n[{message['agent_name']}]\n{message['content']}")
```

**用 `SqliteChannel` 在一个数据库里保存多段对话。** 它对线程和进程都是安全的（该 PR 从 8 个线程并发发布了 40 条消息），`fetch_messages()` 会返回带有 id 和时间戳的行：

```python
from swarms import SqliteChannel

channel = SqliteChannel("runs/channels.db", name="ev-batteries")
SequentialWorkflow(agents=[researcher, analyst, writer], channel=channel).run(
    "Report on the EV battery market."
)

for row in channel.fetch_messages():
    print(row["created_at"], row["agent_name"], row["content"][:80])

SqliteChannel.list_conversations("runs/channels.db")   # ['ev-batteries', ...]
```

**用 `HttpChannel` 在多台机器之间共享一段对话。** URL 指定一段对话，服务器针对它响应三种调用。它使用 `httpx`，而这本来就是一个依赖；`examples/channel_examples/http_channel_server.py` 中附带了一个只用标准库实现的参考服务器：

| 调用 | 服务器做什么 | 请求体/响应体 |
|---|---|---|
| `GET url` | 返回所有消息，最早的在前 | `[{"agent_name": ..., "content": ...}, ...]` |
| `POST url` | 追加一条消息 | `{"agent_name": ..., "content": ...}` |
| `DELETE url` | 删除所有消息 | 无 |

```python
from swarms import Agent, HttpChannel

channel = HttpChannel(
    "https://your-server/channels/ev-report",
    headers={"Authorization": "Bearer ..."},
)
Agent(agent_name="Researcher", model_name="gpt-5.4", channel=channel).run("Report on EVs.")
```

**通过电子邮件把人拉进回路。** `SmtpChannel` 会把每一次发布串进你自己邮箱里的同一个邮件会话，而一个人从 Gmail 或 Outlook 发出的回复会作为一个对话轮次回来，引用的历史内容会被去掉。它只使用标准库，并从环境变量中读取 `SMTP_USERNAME` 和 `SMTP_PASSWORD`。

```python
from swarms import Agent, SmtpChannel

channel = SmtpChannel(
    from_address="agents@yourco.com",
    to="you@yourco.com",
    smtp_host="smtp.yourco.com",
    imap_host="imap.yourco.com",
    subject="EV battery market report",
)

Agent(agent_name="Researcher", model_name="gpt-5.4", channel=channel).run(
    "Report on the EV battery market."
)
```

实现中有几处细节值得一提。邮件正文以精确字节的 base64 形式发送，因为 `Agent.run` 是按精确文本来找到自己的任务的，否则 `set_content` 会多加一个换行。每个实例会按 `Message-ID` 合并自己发布的内容，所以它不依赖于密送副本在下一个智能体读取之前到达。去除引用只作用于人类的回复，所以智能体答案中的 `>` 引用块会被保留下来。`clear()` 要求服务器支持 UIDPLUS 扩展，因为普通的 `EXPUNGE` 还会删掉其他已经被标记为待删除、却与此无关的邮件。文档明确说明不支持 Microsoft 365，因为 Exchange Online 已经不再接受通过 IMAP 使用密码登录。

`AgentMailChannel` 通过 [AgentMail](https://agentmail.to) 的 API 做同样的事，使用 `AGENTMAIL_API_KEY`。它是对着线上 API 构建的，该 PR 也记录了这因此改变了什么。智能体自己发布的内容通过一个 `X-Swarms-Length` 头读回，而不使用 AgentMail 提取出的文本，因为后者会保留免费套餐的页脚，并在 `Sent from my iPhone` 这样的行处把内容截断。另外，只有在标记为 `sent` 的邮件上，智能体相关的头才会被采信，所以一封伪造了 `X-Swarms-Agent` 的回复，没法把话硬塞进某个智能体嘴里。

```python
from swarms import AgentMailChannel

channel = AgentMailChannel(
    inbox_id="research@agentmail.to",
    to="you@example.com",
    subject="EV battery market report",
)
```

**自己写一个。** 任何带有 `post` 和 `messages` 的东西都是一个频道：一个 Redis 列表、一个 Slack 话题、一个你已经在运行的数据库。

```python
from swarms import Agent, CommsChannel

class ListChannel(CommsChannel):
    def __init__(self):
        self.rows = []

    def post(self, agent_name: str, content: str) -> None:
        self.rows.append({"agent_name": agent_name, "content": content})

    def messages(self):
        return list(self.rows)

    def clear(self) -> None:
        self.rows.clear()
```

频道中的行携带的是 `agent_name`，而不是聊天角色。转换成 `user` 和 `assistant` 对话轮次的操作只发生在两个地方：`Agent.run` 和 `Conversation`，所以包里的其他部分永远不会看到频道的原始行。`examples/channel_examples/` 中有十八个可运行的脚本，每个结构一个，另外还有队列、SQLite、HTTP、电子邮件和续跑的示例。

### `PhasedFanOutWorkflow`：一个主导智能体把一次运行规划到许多全新的智能体上

这是一个新结构，面向那些只有在运行时才知道宽度的任务：「找出这些文件里的每一个缺陷，然后逐一验证」，或者「读完每一份合同，然后让每一条候选条款都被独立核查」（[#2599](https://github.com/kyegomez/swarms/pull/2599)）。

```python
from swarms.structs.phased_fan_out_workflow import PhasedFanOutWorkflow

workflow = PhasedFanOutWorkflow(model_name="gpt-5.4", worker_model_name="gpt-5.4-mini")
print(workflow.run("Find every bug in these files and verify each one: ..."))

workflow.last_plan   # the WorkflowPlan the lead wrote
workflow.last_run    # outputs per step, failures, agent count
workflow.usage       # provider tokens over the lead and every worker
```

它分四个阶段工作：

1. **规划。** 主导智能体以 JSON 形式返回一个 `WorkflowPlan`：内联定义的智能体、由步骤组成的各个阶段，以及它想拿回输出的那些步骤。计划是数据而不是代码，所以模型写出的任何东西都不会被执行。
2. **校验。** 未知的智能体、对不在更早阶段中的步骤的引用、出现在扇出之外的 `{item}`、作用于源步骤 `output_schema` 没有声明为数组的字段上的 `for_each`，以及静态的智能体数量，都会在任何东西运行之前被检查。有两项检查来自实际测试。一个不含 `{task}`、`{item}` 或 `{step_id}` 占位符的步骤会被拒绝，因为它的智能体将看不到任何材料。同一阶段中使用相同智能体和相同提示词的两个步骤也会被拒绝，因为它们会做同样的工作。被拒绝的计划会连同错误一起退回给主导智能体，最多 `max_plan_attempts` 次。
3. **执行。** 各阶段按顺序运行，一个阶段内的步骤并行运行，上限为 `max_concurrent_agents`。一个 `for_each` 步骤会为更早某个步骤返回的列表中的每一项运行一个全新的智能体。一个会超过 `max_agents` 的扇出，会在它的任何智能体启动之前就停下。失败的扇出槽位会变成 `None`，并列在 `last_run["failures"]` 中；失败的单个步骤会抛出 `PhasedFanOutWorkflowError`。
4. **合并。** 主导智能体只读取被请求的那些输出，并写出答案。

预定义的智能体每次使用时都会根据它们的构造参数重新构建，因为 `copy.deepcopy(Agent)` 会抛出异常，所以步骤之间、运行之间不会残留任何对话状态。用 `agents=[...]` 传入你自己的智能体，并设置 `allow_inline_agents=False`，就能把主导智能体限制在它们之内：

```python
from swarms import Agent
from swarms.structs.phased_fan_out_workflow import PhasedFanOutWorkflow

reader = Agent(
    agent_name="Clause-Reader",
    agent_description="Reads one contract and quotes any change-of-control clause.",
    system_prompt="You read a single contract and quote, word for word, every clause triggered by a change of control. If there is none, say so.",
    model_name="gpt-5.4-mini",
    max_loops=1,
)
checker = Agent(
    agent_name="Clause-Checker",
    agent_description="Independently checks whether a quoted clause really is a change-of-control clause.",
    system_prompt="You are a skeptical contracts lawyer. Decide whether the quoted clause is triggered by a change of control.",
    model_name="gpt-5.4-mini",
    max_loops=1,
)

workflow = PhasedFanOutWorkflow(
    model_name="gpt-5.4",
    agents=[reader, checker],
    allow_inline_agents=False,
    size_guideline="small",
)
print(workflow.run(task_with_four_contracts))
```

在真实模型上，找缺陷的示例用大约 14,000 个 token 找到并确认了全部三个预埋的缺陷，合同审查的示例在三次运行中三次都找到并引用了两条控制权变更条款。后续的一个修复允许主导智能体的 JSON 后面跟一行收尾的文字说明，这种情况此前会浪费一次规划尝试，或者让一个工作步骤以 `Extra data` 失败（[#2611](https://github.com/kyegomez/swarms/pull/2611)）。两个示例都在 `examples/multi_agent/phased_fan_out_workflow/`。

### `swarms[fast]`：模型调用走 RouteHub，图计算用 rustworkx

`pip install "swarms[fast]"` 会安装 [RouteHub](https://github.com/The-Swarm-Corporation/RouteHub)，swarms 会让每一次模型调用都经由它而不是 litellm（[#2527](https://github.com/kyegomez/swarms/pull/2527)）。无需修改代码。普通的 `pip install swarms` 仍然使用 litellm，行为与以前一致；在已安装 RouteHub 的情况下，`SWARMS_LLM_BACKEND=litellm` 会强制使用 litellm。

```bash
pip install -U "swarms[fast]"

# force litellm even with RouteHub installed
export SWARMS_LLM_BACKEND=litellm
```

包中的每一处 litellm 导入现在都经过同一个模块 `swarms/utils/llm_backend.py`，被选中的库会在第一次模型调用时才导入，而不是在 `import swarms` 时。该 PR 对着一个本地的 OpenAI 兼容服务器做了测量，所以这些数字只反映 swarms 和客户端库本身：

| | v16 | v17，litellm | v17，RouteHub |
|---|---|---|---|
| 总导入时间，含后端 | 1,050 ms | 1,040 ms | 410 ms |
| 从冷启动到第一个答案 | ~1,210 ms | ~1,140 ms | ~580 ms |
| 峰值 RSS | ~220 MB | ~210 MB | ~100 MB |
| 一次 LLM 调用（`LiteLLM.run`） | 1.5 ms | 1.7 ms | 0.67 ms |
| 流式运行 | ~4.8 ms | ~5.3 ms | ~1.2 ms |

使用 RouteHub 时，`set_verbose`、`ssl_verify`、`num_retries` 和 `drop_params` 会随每次调用发送，而不再是模块级全局变量，所以智能体之间不会再互相覆盖设置。`swarms[fast]` 要求 RouteHub 0.2.0 或更新的版本（[#2529](https://github.com/kyegomez/swarms/pull/2529)），这是第一个不再向会拒收 `temperature`、`top_p` 和 `top_k` 的 Claude 模型发送这些参数的版本。在 RouteHub 上有两处行为不同：模型详情来自 OpenRouter 的目录（拉取一次并缓存五分钟），本地服务器需要在 `llm_base_url` 中带上 `/v1`，例如 Ollama 要写成 `http://localhost:11434/v1`。

同一个 extra 现在还会安装 [rustworkx](https://github.com/Qiskit/rustworkx)，也就是 `GraphWorkflow(backend="rustworkx")` 背后的 Rust 图计算库（[#2595](https://github.com/kyegomez/swarms/pull/2595)）。默认后端仍然是 networkx，而且自 [#2590](https://github.com/kyegomez/swarms/pull/2590) 起，networkx、rustworkx 和 graphviz 都要等到构建图时才会加载。

### `DecisionModel`：OpenAI 的 gpt-6-luna、价格，以及每次请求的成本

v16 引入了 `DecisionModel`，用于从 TypeSafe 的 Jev 和 Cloudflare 的 Clef 获得带类型、经过校准的决策。InterLink 新增了第三家 provider，并让每一次调用都可以计价。

**OpenAI 的 Decisions API**（[#2494](https://github.com/kyegomez/swarms/pull/2494)）。`DecisionModel(model_name="gpt-6-luna")` 会使用 `OPENAI_API_KEY` 调用 `https://api.openai.com/v1/decisions`。问题的传入方式和答案的返回形状与另外两家 provider 完全相同，所以切换 provider 只需要换一个模型名：

```python
from swarms import DecisionModel

model = DecisionModel(model_name="gpt-6-luna")

result = model.run(
    state="Export fails in Safari but works in Chrome. I was charged twice for my order.",
    questions={
        "department": {
            "type": "choice",
            "instructions": "Which department should handle this complaint?",
            "criteria": {
                "billing": "Payments, invoices, and refunds.",
                "technical": "Problems using the product.",
                "shipping": "Delivery and tracking.",
            },
        },
        "severity": {
            "type": "score",
            "instructions": "How severe is this issue?",
            "criteria": [
                "Cosmetic: appearance only, no lost functionality.",
                "Workaround available: a task fails, but another way works.",
                "Fully blocked: a task fails with no workaround.",
            ],
        },
        "is_urgent": {"type": "noul", "instructions": "The customer needs a reply today."},
    },
)
```

在底层，`noul` 会变成 OpenAI 的 `predicate`，choice 的 criteria 变成 `choices`，score 的 criteria 变成 `levels`，答案再按问题 id 对回去。字典或列表形式的 state 会以 JSON 发送，一个由 `user` 消息组成的列表会原样透传，所以 `input_image` 部分也能用。这个 provider 用 `httpx` 调用 HTTP API，所以不依赖 `openai`。拒答会抛出 `RuntimeError`，以维持「每个问题都必须拿回一个与自身类型一致的答案」这条规则。线上示例以 0.88 的置信度返回了 `billing`，用了 1,517 个输入 token，花费 $0.000152。

**价格与累计用量**（[#2431](https://github.com/kyegomez/swarms/pull/2431)）：

```python
from swarms import DecisionModel, get_decision_model_prices

get_decision_model_prices()
# {"jev-latest": {"input": 0.042, "output": 0.0}, ..., "clef": {"input": 0.24, ...}, "gpt-6-luna": {"input": 0.10, "output": 0.0}}

model = DecisionModel()
response = model.run(state, questions)

model.usage                            # summed over every request, including choice(), score() and noul()
model.calculate_cost(response["usage"])  # this request
model.calculate_cost()                   # every request so far
# {"input_tokens": 310, "output_tokens": 47, "input_cost": 1.302e-05, "output_cost": 0.0, "total_cost": 1.302e-05}
```

价格以每百万 token 的美元计。TypeSafe 没有公布价格，所以 Jev 模型使用内置的 $0.042 输入价格，输出免费，这与 TypeSafe 自己的 `Usage` schema 所描述的一致。设置了凭据时，Clef 的价格会从 Cloudflare 的模型搜索中实时读取，并带有内置的回退值。`examples/decision_models/simple_openai.py` 是最小化的版本（[#2495](https://github.com/kyegomez/swarms/pull/2495)）。

### 整个自主运行都会流式输出

开启流式时，`LLMManager` 只转发 `delta.content`。在 `max_loops="auto"` 下，几乎每一轮都是一次工具调用（`create_plan`、你的工具、`subtask_done`、`complete_task`），所以一个流式消费者看到的，要么什么都没有，要么最多一句旁白，而位于 `complete_task` 参数里的最终答案根本没有被流式输出过。思考内容被压着，事后才打印出来（[#2636](https://github.com/kyegomez/swarms/pull/2636)）。

`LLMManager.stream_parts` 现在会在模型流式输出的同时，把所有内容逐一产出：正文原样输出，推理内容放在一个 `[thinking]` 标题之后，每一次工具调用放在一个 `[tool call] <name>` 标题之后，后面跟着它的参数片段。

```python
from swarms import Agent

def get_weather(city: str) -> str:
    """Get the current weather for a city.

    Args:
        city: Name of the city.

    Returns:
        A short weather report.
    """
    return {"Paris": "18C and sunny", "London": "12C and raining"}.get(city, "15C and cloudy")

agent = Agent(
    agent_name="Weather-Agent",
    model_name="gpt-5.4-mini",
    max_loops="auto",
    tools=[get_weather],
    print_on=False,
)

for token in agent.run_stream("Get the weather in Paris and London, then tell me which is warmer."):
    print(token, end="", flush=True)
```

```
[tool call] create_plan {"task_description":"Get the current weather in Paris and London...","steps":[...]}
[tool call] get_weather {"city":"Paris"}
[tool call] subtask_done {"task_id":"fetch_paris_weather","summary":"Retrieved ... 18C and sunny.","success":true}
...
[tool call] complete_task {"task_id":"main_task","summary":"...","results":"...Paris is warmer."}
```

每一种流式模式都从同一个来源读取：回调、`run_stream`、`arun_stream`、实时的 Rich 面板（思考内容变暗，工具调用显示为青色），以及详细流式模式，其中的 `token_info` 字典新增了一个 `type` 字段，取值为 `content`、`reasoning` 或 `tool_call`。工具调用总结和 MCP 之后的总结此前运行在一个单独的非流式调用上，现在也会流式输出了。在同一个线上任务中，每次运行的流式事件数从 0 到 63 个，变成了 528 到 784 个，全部九次工具调用都出现在流里。可运行的版本是 `examples/single_agent/capabilities/streaming/auto_loop_streaming_example.py`。

两个相关的修复：即使 `streaming_on` 是关闭的，`streaming_callback` 现在也能收到 token，`CLAUDE.md` 一直以来就是这么写的（[#2473](https://github.com/kyegomez/swarms/pull/2473)）；在 `SwarmRouter` 上调用 `run(..., streaming_callback=fn)` 也不再让 swarm 的构造函数崩溃（[#2500](https://github.com/kyegomez/swarms/pull/2500)）。

### 带并发上限的异步扇出

[#2959](https://github.com/kyegomez/swarms/issues/2959) 中的计划，是让各个扇出结构都运行在 `Agent.arun` 之上，并提供一个由调用方设置的上限。其中三部分已经合入。

`run_agents_concurrently_async` 现在会 await 每个智能体的 `arun`，而不是把 `run` 推到一个线程上，并且接受 `max_concurrency`（[#3093](https://github.com/kyegomez/swarms/pull/3093)）。结果保持输入顺序，第一个异常会向上传播。`None` 表示所有智能体同时运行；小于 1 的值会抛出 `ValueError`，因为 `asyncio.Semaphore(0)` 会永远等下去。

```python
import asyncio
from swarms import run_agents_concurrently_async

results = asyncio.run(
    run_agents_concurrently_async(agents, "Summarise today's news.", max_concurrency=8)
)
```

`CouncilAsAJudge.arun`（[#3096](https://github.com/kyegomez/swarms/pull/3096)）和 `MajorityVoting.arun`（[#3111](https://github.com/kyegomez/swarms/pull/3111)）逐步对应它们的同步版 `run`：每位评审或投票者拿到的都是同样的带类型对话轮次视图，同时调用模型的最多只有 `max_concurrency` 个，选票和裁决按智能体顺序记录，返回值也完全相同。

```python
from swarms import CouncilAsAJudge, MajorityVoting

verdict = await CouncilAsAJudge(model_name="gpt-5.4").arun(response_to_judge, max_concurrency=3)
answer = await MajorityVoting(agents=voters, max_loops=1).arun(question, max_concurrency=2)
```

在 [#2711](https://github.com/kyegomez/swarms/issues/2711) 完成之前，`Agent.arun` 本身仍然是 `asyncio.to_thread(self.run)`，所以今天每个正在运行的智能体仍然占用一个线程，但同一时刻最多只有 `max_concurrency` 个。等原生的 `arun` 合入后，这三者都会直接运行在事件循环上，无需任何其他改动。

### `AgentRearrange` 可以把整个 swarm 作为步骤运行

`AgentRearrange` 现在可以在 `agents=` 中接受整个 swarm，与普通智能体并列，所以 `SwarmRearrange` 不再需要，已被删除（[#2593](https://github.com/kyegomez/swarms/pull/2593)）。任何带有 `name` 和 `run(task)` 方法的东西都可以出现在流程中：出现在顺序步骤里、并行步骤里、出现不止一次，以及在 `run_stream` 之下。

```python
from swarms import AgentRearrange, ConcurrentWorkflow

research_team = ConcurrentWorkflow(name="Research-Team", agents=[analyst_a, analyst_b])
review_team = AgentRearrange(name="Review-Team", agents=[editor, checker], flow="Editor -> Checker")

pipeline = AgentRearrange(
    agents=[planner, research_team, review_team],
    flow="Planner -> Research-Team -> Review-Team",
)
pipeline.run("Assess the HBM supply outlook for 2027.")
```

嵌套的 swarm 收到的任务是到目前为止的整段共享对话，与一个智能体拿到的上下文相同。如果它返回自己的完整历史，这些内容会全部进入外层对话，所以请给内层 swarm 设置 `output_type="final"`，让它只记录自己的答案。原始对象仍可以通过 `pipeline.agents[i].swarm` 访问。

### 一个 `AgentLoader` 统一加载 Markdown、CSV、JSON 和 YAML

智能体的加载原本分散在 `AgentLoader`、`CSVAgentLoader`、`MarkdownAgentLoader` 和 `create_agents_from_yaml` 之中，有四套相互重叠的 schema，还有一份硬编码的允许模型名列表。现在它只是一个类，使用一个 pydantic schema `AgentConfig`，其字段名就是 `Agent` 的参数名（[#2750](https://github.com/kyegomez/swarms/pull/2750)、[#2759](https://github.com/kyegomez/swarms/pull/2759)）。

```python
from swarms import AgentLoader, load_agent_from_markdown, load_agents_from_markdown

loader = AgentLoader(concurrent=True, max_workers=8)

agents = loader.load_agents_from_markdown("agents/")  # every .md in a directory, in sorted order
agents = loader.auto("team.yml")                      # .md, .yaml, .yml, .csv or .json, any case
agents = loader.load_agents_from_csv("team.csv", model_name="gpt-5.4-mini")  # overrides for every agent
result = loader.load_agents_from_yaml("swarm.yaml", return_type="swarm")     # runs the configured SwarmRouter

loader.create_agent_file("team.json", [
    {"agent_name": "Researcher", "system_prompt": "You research.", "max_loops": "auto"},
    {"agent_name": "Writer", "system_prompt": "You write.", "model_name": "gpt-5.4-mini"},
])

researcher = load_agent_from_markdown("agents/researcher.md")
```

未设置的字段会回落到 `Agent` 的默认值，而不是各个加载器自己的默认值（CSV 加载器以前会打开 `autosave`，Markdown 加载器会设置 `context_length=100000`）。任何模型名都被接受。一组别名让现有文件仍能加载：`name`、`description`、`model`、`dynamic_temperature` 和 `streaming`。未知的键会透传给 `Agent`。每一种格式都接受 `max_loops: auto`（[#2757](https://github.com/kyegomez/swarms/pull/2757)），结果按文件中的顺序返回（[#2730](https://github.com/kyegomez/swarms/pull/2730)、[#3064](https://github.com/kyegomez/swarms/pull/3064)），`AgentLoader(concurrent=False)` 会被遵守，`auto()` 也能读回 `create_agent_file` 写出的每一种格式（[#2767](https://github.com/kyegomez/swarms/pull/2767)）。YAML 中嵌套的 `model:` 块（`model_name`、`temperature`、`max_tokens`）现在会被应用；它此前被传给了 `Agent(model=...)`，然后被忽略。

### 一些较小的新增

- **`Agent.list_tools()`**（[#2434](https://github.com/kyegomez/swarms/pull/2434)）在构造完成后立即返回这个智能体能调用的每一个工具的名字：本地工具、MCP 工具、`handoff_task`、`tool_search` 以及自主循环的工具，去重并按稳定的顺序排列。MCP schema 只拉取一次并缓存；无法连接的服务器会被记录进日志而不是抛出异常，这样其他名字仍然能返回。

  ```python
  agent = Agent(tools=[get_weather], mcp_url="http://localhost:8000/mcp", handoffs=[researcher])
  agent.list_tools()
  # ['get_weather', 'lookup_stock', 'handoff_task']
  ```

- **`stopping_token` 会作为停止序列发送**（[#2749](https://github.com/kyegomez/swarms/pull/2749)）。它此前只是被保存而从未被使用，而 `preset_stopping_token` 却给每个智能体都塞上了 `"<DONE>"`。现在 `Agent(stopping_token="<END>")` 会发送 `stop=["<END>"]`，provider 会在那里结束生成，而 `llm_args={"stop": [...]}` 仍然可以覆盖它。默认值是 `None`。
- **`AutoSwarmBuilder.usage` 和 `AutoAgentBuilder.usage`**（[#2572](https://github.com/kyegomez/swarms/pull/2572)、[#2580](https://github.com/kyegomez/swarms/pull/2580)）以与 `Agent.usage` 相同的键报告 provider 的 token 数，包括构建规格时的主管调用。`SwarmRouter.usage` 现在还会统计构建出来的 swarm 保存在字典中的智能体，这覆盖了 `HeavySwarm` 的工作智能体和 `CouncilAsAJudge` 的六位评审（[#2897](https://github.com/kyegomez/swarms/pull/2897)）；在该 PR 的复现中，一个评审团的 `router.usage` 从 110 个 token 变成了真实的 770 个。
- **一个官方 Docker 镜像** [`swarmscorp/swarms`](https://hub.docker.com/r/swarmscorp/swarms)，由一个新的根目录 `Dockerfile` 构建，基于 Alpine 和 Python 3.13，使用非 root 用户，并提供可写的 `/app`（[#2509](https://github.com/kyegomez/swarms/pull/2509)、[#2510](https://github.com/kyegomez/swarms/pull/2510)）。Docker Scout 的发现从 57 个降到 22 个（这 22 个全部位于 litellm 的代理服务器中，而 swarms 从不导入它），镜像也从 363 MB 缩小到 290 MB。`--build-arg PYTHON_VERSION=3.14` 同样可以构建。

  ```bash
  docker run --rm -e OPENAI_API_KEY -v "$PWD:/app" swarmscorp/swarms python agent.py
  ```

- **为编码智能体而准备**（[#2907](https://github.com/kyegomez/swarms/pull/2907)）：面向 Codex、Cursor、Copilot 和 Jules 的 `AGENTS.md` 与 `.github/copilot-instructions.md`；一个 `py.typed` 标记，让类型检查器使用包自带的注解；一份像样的 PyPI 简介和关键词（[#2962](https://github.com/kyegomez/swarms/pull/2962)）；以及写进 README、`CLAUDE.md` 和 `SKILL.md` 的两个托管 MCP 服务器：用于实时文档的 `https://docs.swarms.world/mcp`，以及用于 Marketplace 的 `https://swarms.world/mcp`。
- **新的环境变量开关**，全部是普通的布尔值或数字：`SWARMS_LLM_BACKEND`、`SWARMS_LOG_FILES`、`SWARMS_STRICT_MODEL_CHECK`、`SWARMS_OTEL_EXIT_TIMEOUT` 和 `SWARMS_OTEL_EXPORT_DELAY_MS`，以及供电子邮件频道使用的 `SMTP_USERNAME`、`SMTP_PASSWORD` 和 `AGENTMAIL_API_KEY`。它们都列在 `.env.example` 中。
- **一个 GraphWorkflow 基准测试** `tests/benchmark_graph_workflow.py`（[#3105](https://github.com/kyegomez/swarms/pull/3105)），用休眠的桩节点在 `GraphWorkflow` 和 LangGraph 中构建相同的图，所以它只测量调度和框架开销。在 1,000 个节点的扇出上，swarms 增加了大约 0.1 秒的开销，LangGraph 大约 0.5 秒；每个节点的开销大约是 2 µs 对 80 µs。

| `Agent`、`Conversation` 和输出格式化器中的 yaml、toml 和 sqlite3 | 约 2.5 ms | [#2953](https://github.com/kyegomez/swarms/pull/2953)、[#2965](https://github.com/kyegomez/swarms/pull/2965) |
| 启动线程池和工作区的 `mkdir` | 导入时不写磁盘 | [#2482](https://github.com/kyegomez/swarms/pull/2482)、[#2969](https://github.com/kyegomez/swarms/pull/2969) |

构建一个智能体也变便宜了。在 RouteHub 上，`Agent()` 会下载 OpenRouter 的模型目录，只为了记录几条「may not be supported」警告：联网时要 162 ms，在一台连不上它的主机上则要 **10 秒**。这些检查现在只在 `SWARMS_STRICT_MODEL_CHECK=true` 时才运行，而一个设置了 `context_length` 和 `max_tokens` 的智能体只需 13 ms 就能构建完成，不打开任何连接（[#2942](https://github.com/kyegomez/swarms/pull/2942)）。模型信息在每个进程中每个模型只查一次，而不是每个智能体查两次，这也让 litellm 不再为每一个使用未知模型的智能体打印四次「Provider List」横幅（[#2854](https://github.com/kyegomez/swarms/pull/2854)）。另外，关闭遥测时，`trace_run` 现在会直接返回未经装饰的函数，所以 `Agent.run` 没有任何额外开销（在一个简单方法上，每次调用从 139 ns 降到 47 ns）（[#2945](https://github.com/kyegomez/swarms/pull/2945)）。

### 宽层和扇出以满宽度运行

`ConcurrentWorkflow` 把默认线程池限制在 32 个智能体，`GraphWorkflow` 则把线程池大小设为 CPU 核心数的 95%。模型调用受限于网络，所以 CPU 数量是一个错误的限制：在一台 12 核的机器上，一个 100 节点的层要分 11 个一批地跑。

```python
from swarms import ConcurrentWorkflow, GraphWorkflow

ConcurrentWorkflow(agents=hundred_agents)                 # all 100 at once (was 32)
ConcurrentWorkflow(agents=hundred_agents, max_workers=8)  # throttle explicitly

wf = GraphWorkflow()                         # every node in the widest layer at once
wf = GraphWorkflow(max_parallel_nodes=16)    # cap it
```

独立节点的扇出，每个智能体替换为一次 200 ms 的休眠，取三次运行的中位数（[#2957](https://github.com/kyegomez/swarms/pull/2957)）：

| 节点数 | v16 | v17 | LangGraph |
|---|---|---|---|
| 8 | 0.206 s | 0.204 s | 0.205 s |
| 32 | 0.614 s | 0.208 s | 0.413 s |
| 100 | 2.036 s | **0.211 s** | 1.436 s |
| 256 | 4.877 s | **0.219 s** | 3.280 s |

`GroupChat` 在 asyncio 的默认执行器上收集竞价（在一台 10 核机器上是 14 个工作线程），所以一个 32 个智能体的聊天要分批收集每一轮；现在它按智能体数量设定线程池大小，一个 32 个智能体的轮次从 0.63 秒降到 0.21 秒（[#2524](https://github.com/kyegomez/swarms/pull/2524)、[#2956](https://github.com/kyegomez/swarms/pull/2956)）。原来的上限防护的是 provider 的速率限制，而不是 CPU，所以如果你在智能体数量很多时遇到 429 或连接池警告，请设置 `max_workers` 或 `max_parallel_nodes`。

### 失败会抛出异常，所以 `fallback_swarms` 能起作用了

v16 让失败的 LLM 调用抛出 `AgentLLMError`。InterLink 沿着这个错误往上追到了各个结构，其中有好几个捕获了它，然后返回了一个看起来像答案的东西。`SwarmRouter(fallback_swarms=...)` 只有在 swarm 抛出异常时才会回退，所以在下面的每一种情况中，回退都从未触发。

| `MixtureOfAgents` | 聚合器失败时把 `"Error: ..."` 当作答案返回 | 抛出异常 | [#3063](https://github.com/kyegomez/swarms/pull/3063) |

### 一个扁平的模型循环

一次失败的模型调用会在三层叠加的机制中被重试：litellm 自己的 `num_retries`、`Agent._run` 中的一个尝试循环，以及 `LLMManager` 中一条递归的回退链。在默认的 `retry_attempts=3` 下，一个挂掉的端点在智能体放弃之前，**每个模型最多可能要花 12 次调用**。递归还会让每一次失败在每一层栈帧上各记录一次日志；工具中的一个缺陷会让整个任务在下一个模型上重跑；而 `retry_attempts` 被设置成了一个 litellm 模块级全局变量，litellm 会在第一次重试调用之后把它清掉，所以同一进程中之后的调用从来不会被重试（[#2811](https://github.com/kyegomez/swarms/pull/2811)）。

```python
from swarms import Agent
from swarms.structs.agent import AgentLLMError

agent = Agent(
    agent_name="Analyst",
    model_name="claude-sonnet-5-5",
    fallback_models=["claude-sonnet-5-5", "gpt-5.4", "gemini/gemini-2.5-pro"],  # primary first
    retry_attempts=3,   # retries per model, made by the client: 4 calls at most
)

try:
    agent.run("Summarise the latest FOMC statement.")
except AgentLLMError as error:
    print("every model failed:", error.__cause__)
```

现在由客户端负责重试（`retry_attempts` 会作为 `num_retries` 随每一次请求一起发送，遇到速率限制时按指数退避），`Agent.run` 则在一个扁平的循环中依次尝试 `fallback_models`。只有 `AgentLLMError` 会让它换到下一个模型；其他任何错误都会立即抛出。每次运行都会重新从主模型开始，而以前一次成功的回退会让智能体从此一直停留在回退模型上。`fallback_models` 是整条链，所以要把主模型放在第一个：设置了它之后，`model_name` 会被替换成列表的第一项。`fallback_model_name` 会在构造时并入 `fallback_models`，调用方传入的 `messages` 现在也能送达回退模型了（[#2806](https://github.com/kyegomez/swarms/pull/2806)）。

### 系统提示词就是你要求的那一个

不带 `system_prompt` 的 `Agent()` 以前会发送一段内置的 1,111 个字符的人设，里面还盖着当前的分钟时间戳。这段人设改变了每一个智能体说的话；而且因为这段文字每分钟都在变，它还破坏了在不同分钟构建的智能体之间的 provider 提示词缓存。一个自主智能体会把它放在自己 10,606 个字符的提示词之前发送，此外还有一段被渲染成「loop number {current_loop} out of auto」的循环提示词（[#2738](https://github.com/kyegomez/swarms/pull/2738)、[#2944](https://github.com/kyegomez/swarms/pull/2944)）。

| `system_prompt` | `max_loops=1` | 整数 `max_loops >= 2` | `max_loops="auto"` |
|---|---|---|---|
| 未传入 | **没有系统消息** | 循环提示词 | 自主提示词 |
| 你的文本 | 你的文本 | 你的文本，然后是循环提示词 | 你的文本，然后是自主提示词 |

```python
from swarms import Agent
from swarms.prompts.agent_system_prompts import build_agent_system_prompt

Agent(model_name="gpt-5.4")                                       # sends only your turns
Agent(model_name="gpt-5.4", system_prompt=build_agent_system_prompt())  # the old persona, if you want it
```

有两个修复让余下的提示词名副其实。`safety_prompt_on=True` 把安全提示词存进了对话历史，看起来像是已经生效，却从未发送出去（[#2902](https://github.com/kyegomez/swarms/pull/2902)）。另外，一个没有系统提示词的智能体不再预置一条空的 `System` 行，这一行此前会出现在每一种输出类型和自动保存中（[#2983](https://github.com/kyegomez/swarms/pull/2983)）。

### Claude 5 与当前这一代模型

当前的 Claude 模型会以 HTTP 400 拒收发送过去的 `temperature`，而 Opus 5.5 拒收所有采样参数。v16 修复了默认的 `Agent` 路径；InterLink 修复了其余部分。

- **剩下的每一处硬编码 temperature 都改为 `None`**（[#2444](https://github.com/kyegomez/swarms/pull/2444)）：`swarms chat`、`ReasoningDuo`、`IterativeReflectiveExpansion`、`ContextCompressor` 的摘要器、Markdown 智能体、`MultiAgentRouter`、`ModelRouter` 和 `AutoSwarmBuilder`。
- **`top_p` 默认为 `None`**（[#2443](https://github.com/kyegomez/swarms/pull/2443)），因为各个路由器会同时发送 `temperature` 和 `top_p=1.0`，而当前的 Claude 模型会拒绝这一组合。
- **提示词缓存不再叠加 `cache_control` 标记。** 包装器在调用方自己的消息字典上打标记，所以每个循环都会多保留一个标记：每次请求依次是 3、4、5、6、7 个，而 Anthropic 的上限是 4 个。现在每次都是 3 个（[#2443](https://github.com/kyegomez/swarms/pull/2443)）。
- **`ModelRouter` 路由到真实存在的模型**（[#2604](https://github.com/kyegomez/swarms/pull/2604)、[#2605](https://github.com/kyegomez/swarms/pull/2605)）。它的表中大部分模型已经退役或无法调用（`google/gemini-pro` 甚至不是一个 litellm 的 provider 前缀）。现在它列出的是 `claude-fable-5-1`、各个 5.5 模型、`gpt-5.4`、`gpt-5.4-mini`、`gemini-2.5-pro`、`deepseek-v4-pro`、`mistral-large-latest`、`groq/openai/gpt-oss-120b` 以及两个 OpenRouter 旗舰模型，不向 Anthropic 发送 temperature，并为路由模型提供一个 `model_name` 参数（默认 `gpt-5.4`；此前硬编码为 `gpt-4o`，这个参数则被忽略）。
- **替换了已退役的默认模型。** `AgentJudge`、`ReflexionAgent` 和三个 `GKPAgent` 类默认使用 `openai/o1`，而 OpenAI 已于 10 月 23 日将其下线（[#2964](https://github.com/kyegomez/swarms/pull/2964)）。`ReasoningDuo` 的主智能体无论 `model_name` 怎么写，都运行在一个硬编码的模型上，它的推理智能体则运行在 `gpt-4o` 上，所以要求使用 Claude 时，实际上是在悄悄向 OpenAI 计费（[#2622](https://github.com/kyegomez/swarms/pull/2622)、[#3067](https://github.com/kyegomez/swarms/pull/3067)）。
- **`random_models_on=True` 会调用它选中的模型。** 它以前只是为标签随机选了一个模型，实际调用的仍是原来的那个（[#2535](https://github.com/kyegomez/swarms/pull/2535)）。
- **`MessageTransforms` 使用真实的上下文窗口。** 它假定每个 Claude 和 Gemini 模型都只有 4,096 个 token，所以 `transforms=TransformConfig(enabled=True)` 会在一个 1M token 模型的历史超过 4k 后就开始裁剪（[#2632](https://github.com/kyegomez/swarms/pull/2632)）；而且它在裁剪时会丢掉系统提示词和 `MEMORY.md` 前言，因为它只匹配小写的 `system` 角色（[#2977](https://github.com/kyegomez/swarms/pull/2977)）。

### 对话：读取更便宜，并且只基于一份历史构建

- **token 计数按消息缓存**（[#2477](https://github.com/kyegomez/swarms/pull/2477)、[#2503](https://github.com/kyegomez/swarms/pull/2503)、[#2552](https://github.com/kyegomez/swarms/pull/2552)）。每一次读取历史都会对整段对话记录做分词，而智能体每个循环要读好几次。读取 200 条消息（约 65k 个 token）从 28 ms 降到 2 ms，裁剪到窗口大小时从 49 ms 降到 3 ms。`ContextCompressor` 每次检查都会对整段历史分词，所以在 160 轮中它分词了 1,135 万个字符；现在只有 41 万个。把 1,000 条短消息首次读入一个 200 token 的窗口，只需调用分词器 15 次，而不是 1,007 次。`Conversation.count_history_tokens()` 成为公开方法，压缩器现在也用智能体自己的分词器来计数。
- **`Transcript` 并入了 `Conversation`**（[#2557](https://github.com/kyegomez/swarms/pull/2557)）。`Agent._run` 在 `short_memory` 旁边还维护着第二份历史，发送给模型的是那一份。现在每一个请求都由 `short_memory.to_messages(...)` 构建。可见的效果：「Current Internal Reasoning Loop n/m」标记行没有了；第二次 `run()` 会把之前的工具调用作为真正的工具调用发送，而不是字符串化的文本；在整数循环中，压缩摘要也终于真正进入了请求。净减少 154 行。
- **压缩调用会计入 `agent.usage`**（[#2722](https://github.com/kyegomez/swarms/pull/2722)）。在一次长运行中，它通常是单次最大的请求，而它恰恰是总数里漏掉的那一个。
- **`"str"`、`"string"` 和 `"all"` 输出类型返回整段对话**（[#3100](https://github.com/kyegomez/swarms/pull/3100)）。它们以前返回的是模型上下文视图，被裁剪到 8,192 个 token，并且在单词中间截断，所以一旦对话记录超过大约 8k 个 token，`AgentRearrange` 和 `SequentialWorkflow`（它们的默认值是 `"all"`）就会悄悄丢掉任务和最前面几个智能体的答案。发送给模型的上下文仍然像以前一样被裁剪。
- **加载和导出名副其实。** `Conversation(load_filepath=...)` 会忽略这个文件（[#2460](https://github.com/kyegomez/swarms/pull/2460)），而 `export_conversation("backup.json")` 会覆盖自动保存的文件，而不是写出 `backup.json`（[#2532](https://github.com/kyegomez/swarms/pull/2532)）。

### MCP

- **`mcp_url` 永远不会被当作命令运行**（[#2724](https://github.com/kyegomez/swarms/pull/2724)）。一个不带协议头的 `mcp_url` 会被当作 stdio 服务器：这个字符串按空格切分后被启动，并且带着宿主机的完整环境，包括每一个 API 密钥。任何能控制一个智能体 `mcp_url` 的人（一个请求体、一个 Markdown 智能体文件的 frontmatter、一份配置）都能运行一条命令。现在 stdio 服务器只能通过显式的 `MCPConnection(command=..., args=[...])` 启动，使用的是 MCP SDK 的最小默认环境，再加上这个连接自己的 `env`。

  ```python
  from swarms import Agent, MCPConnection

  agent = Agent(
      agent_name="Local-Tools",
      model_name="gpt-5.4",
      mcp_config=MCPConnection(
          command="python",
          args=["server.py"],
          env={"API_KEY": "env:API_KEY"},   # pass what the server needs, explicitly
      ),
  )
  ```

- **共享同一个 `MCPConnection` 的两个智能体各自保留自己的凭据**（[#2975](https://github.com/kyegomez/swarms/pull/2975)）。管理器会把自己的默认值写到调用方的对象上，所以在该 PR 的复现中，`bob` 用 `alice` 的 token 向服务器做了认证。现在每个管理器都在一份副本上工作。
- **OAuth 可以用于在某个路径下提供资源的服务器**（[#2905](https://github.com/kyegomez/swarms/pull/2905)），也就是常见的 `/mcp` 部署方式。之前交给 provider 的是服务器的源（origin），所以 SDK 在到达授权服务器之前，就拒绝了服务器声明的资源。
- **只有单个服务器的智能体不再把本地工具调用发给 MCP 服务器**（[#2445](https://github.com/kyegomez/swarms/pull/2445)），服务器会回答 `Unknown tool`，而模型会把它当作工具的结果来读。
- **`MCPDeployer` 可以再次启动**，无论是在 `stop()` 之后、一个 `with` 块之后，还是在第一次 `start()` 因为端口被占用而失败之后。那次失败会在套接字绑定之前就耗掉 MCP 会话管理器（[#2974](https://github.com/kyegomez/swarms/pull/2974)）。

### 遥测：记录一次运行做过的一切，经过压缩，关闭就是真的关闭

和 v16 一样，遥测默认开启。它记录的内容在这个版本中有了相当大的变化，所以这里把它说清楚。

**记录了什么**（[#2504](https://github.com/kyegomez/swarms/pull/2504)、[#2505](https://github.com/kyegomez/swarms/pull/2505)）。每一个被追踪的调用都会记录它的全部参数（`swarms.inputs`）以及发起它的那个结构的完整对话（`swarms.conversation`）。每一次 `Agent.run` 都会记录它使用的 token（`swarms.usage.*`）。每一次模型调用都有自己的 `Agent.llm_call` span，带有延迟、模型、结束原因、确切的请求（`swarms.request`）以及 provider 的完整响应（`swarms.response`）。`swarms.output` 会被完整记录。旧的 `log_agent_data` 快照已被移除，它们在历史超过 65,536 个字符后，到达时 JSON 已经在中间被截断。

**脱敏了什么**（[#2501](https://github.com/kyegomez/swarms/pull/2501)）。任何名字表明是凭据的字典键（以 `key` 或 `token` 结尾，或包含 `secret`、`password`、`authorization` 或 `oauth`，另外还有 headers 和 `env`），其值在所有地方都会被替换为 `<redacted>`，包括 `MCPConnection` 内部。错误日志也不再转储智能体的整个状态。**消息文本和参数值不会被清洗**，所以你粘贴进提示词里的密钥会原样发送。

**如何关闭：**

```bash
export SWARMS_TELEMETRY_ON=False
```

现在关闭就是真的关闭：`trace_run` 会原样返回你的方法，不加任何装饰，也不会导入任何 OpenTelemetry 模块（[#2945](https://github.com/kyegomez/swarms/pull/2945)、[#2967](https://github.com/kyegomez/swarms/pull/2967)）。这个开关在导入 swarms 时读取，`.env` 文件也算在内。

**如何发送。** 导出数据发往 `https://telemetry.swarms.world`，用 zstd 压缩，必要时回退到 gzip（[#2506](https://github.com/kyegomez/swarms/pull/2506)、[#2544](https://github.com/kyegomez/swarms/pull/2544)），在运行过程中每 500 ms 发送一次，而不是在退出时一次性发送（[#2869](https://github.com/kyegomez/swarms/pull/2869)），使用的是在初始化时就打开的连接。退出时的刷新最多一秒，所以一个无法连接的收集器不会再把进程拖住八秒（[#2484](https://github.com/kyegomez/swarms/pull/2484)），而导出失败或启动步骤失败也永远不会打印信息或抛出异常（[#2856](https://github.com/kyegomez/swarms/pull/2856)）。在一个 150 次运行的工作负载上，301 个 span 中有 283 个在运行过程中就已发出，退出刷新从 441 ms 降到 44 ms。

### 除非你要求，否则什么都不写入磁盘

一个导入了 swarms 并运行了一个 `SequentialWorkflow` 的 v16 进程，会留下一个 `agent_workspace/` 目录、一个 `error.txt`、一个每日日志文件、各模块的日志，以及一个 `conversation_history.json`。InterLink 默认一个都不写。

| 内容 | v16 | v17 | PR |
|---|---|---|---|
| `agent_workspace/` 和 `error.txt` | 由 `import swarms` 创建 | 在第一次真正写入时创建 | [#2969](https://github.com/kyegomez/swarms/pull/2969) |
| `WORKSPACE_DIR/logs` 下的日志文件 | 总是写入 | 只在 `SWARMS_LOG_FILES=True` 时写入 | [#2776](https://github.com/kyegomez/swarms/pull/2776) |
| `SequentialWorkflow`、`ConcurrentWorkflow`、`AgentRearrange` 的自动保存 | 开启；`SwarmRouter` 的 `autosave=False` 传不到它们那里 | 关闭；`AgentRearrange(autosave=True)` 现在真的会保存 | [#2943](https://github.com/kyegomez/swarms/pull/2943) |
| `SpreadSheetSwarm` 的 CSV 和 JSON | 开启 | 关闭 | [#2507](https://github.com/kyegomez/swarms/pull/2507) |
| 在导入之后设置 `WORKSPACE_DIR` | 在进程余下的时间里被忽略 | 每次调用时读取 | [#2984](https://github.com/kyegomez/swarms/pull/2984) |

当你确实选择开启时，自动保存的 JSON 会以紧凑格式而不是缩进格式写出，速度大约快 1.3 到 1.5 倍（[#2970](https://github.com/kyegomez/swarms/pull/2970)），而 `create_file_in_folder` 会拒绝那些解析后位于文件夹之外的文件名（[#2939](https://github.com/kyegomez/swarms/pull/2939)）。

### 工具

- **`tool_call_summary` 默认为 `False`**（[#2432](https://github.com/kyegomez/swarms/pull/2432)）。每次工具调用之后，智能体都会再发起一次模型调用，把输出总结进 `short_memory`，而模型从来不读它。在 Haiku 上，这让每次工具轮次多花 2.0 到 2.8 秒。现在一次工具轮次就是一次模型调用。
- **嵌套的 Pydantic 参数会生成有效的 schema**（[#2541](https://github.com/kyegomez/swarms/pull/2541)）。一个接受 `items: list[LineItem]` 的工具发出的 `$ref` 指向一个不存在的位置，因为每个参数的 `$defs` 都留在了参数内部。现在它们被提升到了根部。一个同时有名为 `type` 和 `title` 两个字段的模型，也不再从它的 properties 中丢掉 `title`（[#2462](https://github.com/kyegomez/swarms/pull/2462)）。
- **一组 Anthropic 风格的工具调用中，每个工具只运行一次**，而不是两次（[#2570](https://github.com/kyegomez/swarms/pull/2570)）；`Agent(list_base_models=[...])` 也能正常构造并发送真正的 schema，而不是先抛出 `TypeError`、再把它们重复编码（[#2571](https://github.com/kyegomez/swarms/pull/2571)、[#2577](https://github.com/kyegomez/swarms/pull/2577)）。
- **单 CPU 的主机也能构建智能体了。** `int(os.cpu_count() * 0.8)` 在单核上等于 0，所以在 1 vCPU 的容器上，每一个 `Agent(tools=[...])` 都会抛出异常。现在工具 schema 在一个普通循环中构建，`HeavySwarm` 则使用一个永远不会返回小于 1 的辅助函数（[#2468](https://github.com/kyegomez/swarms/pull/2468)、[#2598](https://github.com/kyegomez/swarms/pull/2598)）。
- **自主循环在多次运行之间复用它的客户端和工具 schema**（[#2521](https://github.com/kyegomez/swarms/pull/2521)）：第一次运行之后不再重建客户端（以前每次运行要重建两次），而一个带十个工具的自主 `run()` 在 swarms 内部只花 0.69 ms，而不是 1.83 ms。`max_subtask_iterations` 现在会像文档写的那样统计 LLM 调用次数；它以前统计的是子任务数，所以真正的上限是标称值的 20 倍（[#2308](https://github.com/kyegomez/swarms/pull/2308)）。

### `CronJob`

四个修复让 `CronJob` 可以被停止、也可以重新启动。`stop()` 会等待一个事件，而不是一次一秒的休眠，所以停止十个空闲任务只需不到一秒，而不是七秒（[#2488](https://github.com/kyegomez/swarms/pull/2488)）。一个停止的任务重新启动时，不会再带着一份每个节拍运行两次任务的过期调度，不会带着一份已经耗尽的错误预算，也不会多出第二个调度线程（[#2567](https://github.com/kyegomez/swarms/pull/2567)）。另外，一个任务可以在它自己的智能体或回调中停止自己，这在以前会抛出 `cannot join current thread`（[#2639](https://github.com/kyegomez/swarms/pull/2639)）：

```python
from swarms import CronJob

runs = []

def report(output, task, metadata):
    runs.append(output)
    if len(runs) == 3:
        job.stop()   # safe from inside the job now
    return output

job = CronJob(agent=agent, interval="1hour", callback=report)
job.run("Summarise the overnight alerts.")
```

### 路由器和较小的结构

- **`SwarmRouter` 按照文档描述的方式构建每个 swarm。** `MixtureOfAgents` 只把最后一个智能体用作聚合器，而以前它同时还作为工作智能体运行，并评判自己的答案（[#2732](https://github.com/kyegomez/swarms/pull/2732)）。`RoundRobin` 会返回路由器的 `output_type`（[#2731](https://github.com/kyegomez/swarms/pull/2731)）。`GroupChat` 会得到 `max_loops` 个智能体轮次，而以前默认值 1 意味着零个轮次，因为用户的消息被算作了第一条（[#2755](https://github.com/kyegomez/swarms/pull/2755)）。
- **`AutoSwarmBuilder.initialize_swarm_router` 会告诉主管它有哪些智能体**（[#2898](https://github.com/kyegomez/swarms/pull/2898)），这样它写出的流程里用的是真实存在的智能体名，而不是凭空编造、随后被 `AgentRearrange` 拒绝的那些。
- **`TreeAgent` 的路由能正常工作了**（[#2620](https://github.com/kyegomez/swarms/pull/2620)、[#2990](https://github.com/kyegomez/swarms/pull/2990)）。它排名最高的关键词是 `you`、`are` 和 `a` 这样的词，还以子串方式匹配，所以树中的第一个智能体会揽下所有任务。另外，按文档写法 `TreeAgent(name=...)` 构建出来的是一个没有名字的智能体，其 `ForestSwarm.run` 会返回 `None`。
- **`AdvisorSwarm`** 以各个智能体自己的名字记录对话轮次，所以自定义的执行者不会再把自己写的代码当作别人的来读（[#2543](https://github.com/kyegomez/swarms/pull/2543)）。**`SelfMoASeq`** 会把 `max_tokens` 传给它的智能体，并且不再生成那些永远不会被聚合的样本（[#3065](https://github.com/kyegomez/swarms/pull/3065)）。**`AgentRouter`** 不再在嵌入历史文本时在每个字符之间插入一个空格（[#2597](https://github.com/kyegomez/swarms/pull/2597)）。**`AgentRegistry.find_agent_by_id`** 能正常工作了（[#2773](https://github.com/kyegomez/swarms/pull/2773)）。在 Python 3.12 及以后的版本上，原始 base64 图片又能被识别了（[#2809](https://github.com/kyegomez/swarms/pull/2809)）。
- **CLI**：`swarms init` 会就地更新已有的 `.env`，而不是覆盖它并删掉不相关的键（[#3057](https://github.com/kyegomez/swarms/pull/3057)）；`swarms load-markdown` 可以加载一个目录（[#2766](https://github.com/kyegomez/swarms/pull/2766)）；未知命令会以状态码 2 退出（[#2760](https://github.com/kyegomez/swarms/pull/2760)）。

## 10 月 2 日，星期五

**`1152457`** · [#2420](https://github.com/kyegomez/swarms/pull/2420) · **fix(`GroupChat._decide_sync`)：以 output_type final 读取每一次竞价，让使用默认 output_type 的智能体也能发言**

`GroupChat` 从 `agent.run()` 的返回值中读取每个智能体的竞价。在默认的 `output_type="str-all-except-first"` 下，这个值是之前的对话轮次再加上那次工具调用，所以解析失败，每一次竞价都变成了 `(0.0, "")`，聊天在用户的消息之后就结束了。**按照 `CLAUDE.md` 中 GroupChat 示例的方式构建的智能体，永远无法发言。** 现在每一次竞价都以 `output_type="final"` 运行，并在 `finally` 中恢复智能体自己的值，所以一个在聊天之外被复用的智能体会保持调用方构建时的样子。第一轮的警告也把无法解析的 `respond()` 回复列为一种可能的原因，而以前它会让用户去检查自己的 API 密钥。

**`a388e08`** · [#2432](https://github.com/kyegomez/swarms/pull/2432) · **fix(`Agent.__init__`)：把 tool_call_summary 默认设为 False，让一次工具轮次只有一次模型调用**

开启总结时，`ToolManager.execute_tools` 会在每次工具执行之后新建一个客户端，并让它总结输出。**这份总结只进入了 `short_memory`，而模型从来不读它**，因为后续请求本来就带着原始的工具结果。每一次工具轮次都为一次往返付出了两次往返的代价；该 issue 测得，仅总结这一步在 Haiku 上就要 2.0 到 2.8 秒。`tool_call_summary=True` 会完全保留原来的行为。

v16 的 #2393 修复了 `Agent` 和 `LiteLLM`，但仍有八条路径强制设置了 temperature：`swarms chat`（1.0 外加动态 temperature）、`ReasoningDuo` 和 `IterativeReflectiveExpansion`（动态 temperature）、`ContextCompressor` 的摘要器（0.2）、文件中没有写 temperature 的 Markdown 智能体（0.1）、`MultiAgentRouter`（0.1）、`ModelRouter`（0.5）以及 `AutoSwarmBuilder` 的规格调用（0.5）。现在它们都默认为 `None`。调用方显式传入的值仍会被发送。

**`da7aaad`** · [#2445](https://github.com/kyegomez/swarms/pull/2445) · **fix(`MCPManager._route`)：即使只有一个服务器，也只把调用发给提供了该工具的服务器**

只配置了一个 MCP 服务器时，`_route` 会把每一个未知的工具名都发给它，所以同一轮中的本地工具调用和 `handoff_task` 都去了服务器那里，服务器回答 `Unknown tool: get_weather`，而模型把它当成了结果来读。为这条捷径辩护的那条注释已经不再成立：工具发现本来就在路由之前运行，并且有缓存。现在只有一个服务器时，行为与有多个服务器时完全一致。

**`f04d72c`** · [#2443](https://github.com/kyegomez/swarms/pull/2443) · **fix(`LiteLLM`)：把 top_p 默认设为 None，并让提示词缓存不再叠加 cache_control 标记**

## 10 月 5 日，星期一

**`61e7ae6`** · [#2468](https://github.com/kyegomez/swarms/pull/2468) · **fix(`convert_multiple_functions_to_openai_function_schema`)：在一个普通循环中构建工具 schema，让单 CPU 的主机不再崩溃**

线程池的大小是 `int(os.cpu_count() * 0.8)`，在单 CPU 上等于 0，而 `ThreadPoolExecutor(max_workers=0)` 会抛出异常。**在 1 vCPU 的容器或 CI 运行器上，每一个 `Agent(tools=[...])` 都在构造时失败。** schema 的构建是受 GIL 约束的纯 Python 代码，所以这些线程本来也从未真正并行过；因此线程池被直接去掉，而不是加一层防护。

**`6ba083a`** · [#2471](https://github.com/kyegomez/swarms/pull/2471) · **fix(`LLMManager.switch_to_next_model`)：在按 fallback_model_name 切换之后，把主模型保留在回退链中**

在 `fallback_model_name=B` 时，第一次切换会覆盖 `model_name`，回退链只根据回退模型重新计算，于是在这个智能体上再也回不到主模型了。现在回退链会在覆盖之前被固定下来。这个问题只有在 v16 让失败的运行抛出异常之后才会触发。（#2811 后来用一个扁平循环替换了整套机制。）

**`21bd448`** · [#2477](https://github.com/kyegomez/swarms/pull/2477) · **perf(`Conversation.return_history_as_string`)：按消息统计 token，并在多次读取之间复用**

在默认的 `dynamic_context_window=True` 下，每一次读取历史都会对整段对话记录运行 `count_tokens()`，而智能体每个循环要读好几次；一旦历史超过 `context_length`，一次字符级的二分查找还要再分词大约 17 次。现在计数按格式化后的消息缓存。**200 条消息（约 65k 个 token）：每次读取 28 ms → 2 ms，裁剪时 49 ms → 3 ms。** 只要历史放得下，输出就与之前逐字节一致。

**`52db07e`** · [#2473](https://github.com/kyegomez/swarms/pull/2473) · **fix(`LLMManager.call`)：即使 streaming_on 是关闭的，也向 streaming_callback 流式输出**

`CLAUDE.md` 中「把 token 流式输出到回调」的示例只传了 `streaming_callback` 而没有传 `streaming_on`，结果回调什么也收不到：`LLMManager.call` 只在设置了 `streaming_on` 时才进行流式输出。现在，有回调本身就足以开启流式，而且 `imgs` 在每一条路径上都能送达模型。作为结果，`ConcurrentWorkflow` 的仪表盘智能体现在也会实时流式输出。

**`95025a5`** · [#2482](https://github.com/kyegomez/swarms/pull/2482) · **perf(`MCPManager`)：惰性导入 mcp，并去掉启动线程池**

`import swarms` 和 `Agent(...)` 不再加载 `mcp`，这原本要花大约 0.4 秒。只用于类型标注的导入被移到 `TYPE_CHECKING` 之下，`MCP_IS_V2` 变成一个带缓存的函数，启动过程也在一个普通循环中而不是线程池中设置日志级别。`import swarms`：1.81 s → 1.52 s。

**`d5ef38b`** · [#2483](https://github.com/kyegomez/swarms/pull/2483) · **fix(`bootup`)：在无法创建工作区时，让 import swarms 继续正常工作**：上一个 PR 去掉了包在工作区创建外面的防护，所以在一个只读的工作目录（AWS Lambda）中，导入会以 `PermissionError` 失败。这一步的防护已经恢复。

**`c3bacf8`** · [#2484](https://github.com/kyegomez/swarms/pull/2484) · **perf(`telemetry/otel.py`)：在第一次追踪时加载 OpenTelemetry，并为退出时的刷新设上限**

## 升级须知

1. **给你的智能体一个系统提示词。** 不带系统提示词的 `Agent()` 现在什么都不发送。如果你的智能体依赖那段内置的人设，请从 `swarms.prompts.agent_system_prompts` 中导入并传入 `system_prompt=build_agent_system_prompt()`。
2. **预期 swarm 会抛出异常。** `HeavySwarm`、`MixtureOfAgents`、`MajorityVoting`、`AuctionSwarm` 以及 `AgentRearrange` 的并行步骤，在以前返回错误字符串的地方现在会抛出异常。捕获这个异常，或者在 `SwarmRouter(fallback_swarms=[...])` 之下运行它们，后者现在真的会回退了。provider 错误以 `AgentLLMError` 的形式到达，原始错误作为 `__cause__`。
3. **在需要的地方重新开启文件输出。** 给 `SequentialWorkflow`、`ConcurrentWorkflow`、`AgentRearrange` 或 `SpreadSheetSwarm` 传入 `autosave=True`，需要日志文件时设置 `SWARMS_LOG_FILES=True`。
4. **替换已移除的结构和加载器。** `SwarmRearrange` 改为 `AgentRearrange(agents=[...swarms])`；`create_agents_from_yaml`、`CSVAgentLoader` 和 `MarkdownAgentLoader` 改为 `AgentLoader`；`ImageAgentBatchProcessor` 现在位于视觉示例中。
5. **搜索已移除的关键字参数。** `multi_modal`、`sop`、`sop_list`、`output_cleaner`、`agents_config`、`memory_system`、`shared_memory_system` 和 `shared_memory` 现在会被静默忽略。`n`、`idle_timeout`、`auto_generate_prompts` 和 `output_metadata` 会抛出 `TypeError`。`bulk_run` 和回退链相关的方法都已不复存在。
6. **如果你的 provider 对你限速，请设置并发上限。** `ConcurrentWorkflow` 和 `GraphWorkflow` 现在会让一层中的所有智能体同时运行：请使用 `max_workers` 和 `max_parallel_nodes`。
7. **把 stdio MCP 服务器迁移到 `MCPConnection(command=..., args=[...])`**，并显式传入它们需要的环境变量。
8. **检查流式消费者收到了什么。** 回调和 `run_stream` 现在会包含位于 `[tool call]` 和 `[thinking]` 标题之后的工具调用和思考文本。
9. **审视遥测。** 它会记录完整的对话、参数、请求和响应，以凭据命名的键会被脱敏，消息文本则原样发送。设置 `SWARMS_TELEMETRY_ON=False` 即可退出。
10. **安装 `swarms[fast]`。** RouteHub 和 rustworkx 都可以直接替换使用，`SWARMS_LLM_BACKEND=litellm` 可以切换回去。

## 接下来

未解决的问题都明确写了下来，而不是暗示一下了事：

- **为 `GraphWorkflow` 引入就绪队列调度**（[#3102](https://github.com/kyegomez/swarms/issues/3102)）。swarms 和 LangGraph 都要等一整层完成之后才开始下一层，所以在基准测试中那张错落的图上，两者都要 1.61 秒，而理论上 0.55 秒就够了。在每个节点自己的依赖一完成时就启动它，是下一个大幅提速的来源。
- **原生异步的 `Agent.arun`**（[#2711](https://github.com/kyegomez/swarms/issues/2711)）。在它合入之前，每一个被 await 的智能体仍然占用一个线程；合入之后，这个版本中的异步扇出辅助函数会直接运行在事件循环上，无需任何其他改动，[#2959](https://github.com/kyegomez/swarms/issues/2959) 的其余部分也可以随之跟进。
- **为 `GraphWorkflow` 提供带类型的事件流和 `on_error` 策略**（[#3103](https://github.com/kyegomez/swarms/issues/3103)、[#3104](https://github.com/kyegomez/swarms/issues/3104)），让调用方可以逐个节点地观察一张图的运行，并决定一个失败的节点是否让它停下。
- **自主循环自己的对话记录。** #2557 把整数循环迁移到了 `short_memory` 上；`max_loops="auto"` 仍然维护着一个单独的请求 `Conversation`，因为它的工具处理器会把结果的文字副本写进记忆（[#2386](https://github.com/kyegomez/swarms/issues/2386) 的其余部分）。
- **`HierarchicalSwarm` 和 `MixtureOfAgents` 的线程池**仍然默认为 CPU 核心数的 95%，而这正是 #2956 和 #2957 在别处去掉的那个限制。
- **litellm 的版本固定。** 剩下的 22 个 Docker Scout 发现全部位于 litellm 的代理服务器中，升级到 litellm 1.88.6 或更新的版本即可清除，但这是一次跨越十二个次版本的升级，需要单独的一轮测试。
- **遥测数据的大小。** 每一个运行 span 都会重新发送到目前为止的对话，所以导出数据的大小随轮数的平方增长。zstd 目前能让它保持在收集器的上限之内；只发送自上一个 span 以来的新消息，就能消除这种增长。
- **电子邮件频道的线上检验。** `SmtpChannel` 的会话搜索还没有在 Gmail、Microsoft 365 和 Dovecot 服务器上实际运行过，`AgentMailChannel` 也还没有在付费套餐或欧盟节点上运行过。
- **频道的文档。** 文档站点的 Comms Channel 页面还在一个未合入的文档 PR 中；在它合入之前，请以 `examples/channel_examples/` 为准。
