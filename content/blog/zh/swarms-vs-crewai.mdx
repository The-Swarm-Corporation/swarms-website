# Swarms 与 CrewAI 对比：多智能体框架该选哪一个？

如果你已经用 CrewAI 搭过东西，你就知道问题的形态。角色、任务、crew、kickoff。它让你的原型跑了起来。现在的问题是：它是否值得你在接下来一年里放进生产环境。

该给的肯定要给：CrewAI 的 `role`、`goal`、`backstory` 和 `expected_output` 这套词汇读起来很顺，新同事不看教程也能读懂一份 crew 定义。这是真诚的称赞，而对比也就在这里不再势均力敌。

本文会用两者搭建同一份工作，然后从决定生产系统成败的三件事出发论证 Swarms：可测量的性能、运维面，以及你必须自己承担的部分。

## 已发表的性能工作

先从这个类别里没有第二家拿得出的东西说起：一篇可供同行评议的系统论文，以及一套开放的基准测试。

Swarms 研究团队发表了 **["GraphWorkflow：一个面向多智能体系统的低开销一次编译图执行引擎"](https://github.com/The-Swarm-Corporation/GraphWorkflow-Paper/blob/main/main.pdf)**，这是对驱动 Swarms 编排的图引擎的一次完整系统性论述。在一套开放测试集上，覆盖 5 种拓扑、10 到 200 个节点、15 组拓扑与规模配置，每个数字都是 9 次采样的中位数并带 95% 置信区间：

- 在已编译图的执行上，相对 LangGraph 取得 **7.0 倍的几何平均加速**
- **200 节点链式图上 62.5 倍**，0.29 毫秒对 18.15 毫秒
- 即使在浅而宽的图上也有 **2.7 到 4 倍**
- 图的编译速度快 **21.6 到 31.3 倍**
- 冷启动的构建、编译、执行全路径快 **7.9 倍**

上述每一个数字都可以用[公开的测试工具](https://github.com/The-Swarm-Corporation/GraphWorkflow-Paper/tree/main/benchmarks)复现，原始采样数据和分析流程随论文一并发布。我们的[论文完整解读](/zh/blog/graphworkflow-research-paper)梳理了成本分类，以及每一处实测差距的归因。

这正是关键区别。这个领域里的大多数智能体框架，包括 CrewAI，交付的是关于速度的营销说辞。Swarms 交付的是一篇论文、一套测试工具和原始 JSON 数据，并邀请任何人在自己的硬件上重跑一遍。

## 关于速度的结构性论证

上面的数字是针对 LangGraph 的，因为现成的基准测试就是它。但这些数字衡量的设计差异并不只针对 LangGraph，把它当作架构问题而不是比分牌来理解更有价值。

CrewAI 所属的那一类，也就是进程内的 Python 编排库，在每一次运行时都会做两件事：从你的任务与依赖定义中重新推导执行顺序，并且在你自己的进程里跑编排循环。这意味着准备工作是按次付费而不是一次付清，而你的吞吐上限就是你的解释器、你的线程池、你的那台机器。

Swarms 把这两半都反了过来。图只编译一次，固化成一份执行计划，之后的重复运行只是扫过这份计划，而不是重建它。编排本身作为托管服务运行，因此上限属于平台，而不是你的进程。用论文里的说法，单次运行的成本收敛到边际执行项，而这正是深链上 62.5 倍的来源。

对于一次原型运行，这一切在模型延迟面前都看不出来。但在高请求速率下、在评估扫描中、在冷启动时，它就是全部。

## 同一条流水线的两种写法

一个研究智能体把工作交给一个分析智能体，顺序执行。

### CrewAI

```python
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Researcher",
    goal="Gather the facts on the given market",
    backstory="A thorough analyst who cites sources.",
    verbose=False,
)

analyst = Agent(
    role="Analyst",
    goal="Turn research into a decision-ready brief",
    backstory="A skeptical reviewer who flags weak claims.",
    verbose=False,
)

research_task = Task(
    description="Research the EV battery supply chain in 2026.",
    expected_output="A factual summary with sources.",
    agent=researcher,
)

analysis_task = Task(
    description="Write a decision brief from the research.",
    expected_output="A one-page brief with a recommendation.",
    agent=analyst,
    context=[research_task],
)

crew = Crew(
    agents=[researcher, analyst],
    tasks=[research_task, analysis_task],
    process=Process.sequential,
)

print(crew.kickoff())
```

它跑在你把它放到的任何地方。模型凭证、进程、守护、重试逻辑，以及凌晨三点让它继续活着的那一套，都由你提供。

### Swarms

```python
import httpx

payload = {
    "name": "Research Swarm",
    "description": "A two-agent research and analysis pipeline",
    "swarm_type": "SequentialWorkflow",
    "task": "Research the EV battery supply chain in 2026 and write a decision brief.",
    "agents": [
        {
            "agent_name": "Researcher",
            "description": "Gathers the facts on the given market",
            "system_prompt": "Research thoroughly and cite sources.",
            "model_name": "claude-sonnet-5",
            "fallback_model_name": "gpt-4.1",
            "max_loops": 1,
        },
        {
            "agent_name": "Analyst",
            "description": "Turns research into a decision-ready brief",
            "system_prompt": "Write a one-page brief. Flag weak claims.",
            "model_name": "gpt-4.1",
            "max_loops": 1,
        },
    ],
    "max_loops": 1,
}

response = httpx.post(
    "https://api.swarms.world/v1/swarm/completions",
    headers={"x-api-key": "YOUR_API_KEY"},
    json=payload,
    timeout=300.0,
)

print(response.json())
```

同一条流水线，一个 HTTP 请求，没有任何东西需要你维持运行。如果你不想手写这个调用，官方 SDK 也都在：Python 用 `pip install swarms-client`，TypeScript 用 `npm install swarms-ts`，此外还有 Go、Java 和 C#。任何能发出 HTTP 请求的语言都是一等客户端。

这份负载里有三个字段承载了大部分杠杆。

**`swarm_type` 只是一个字段。** 把 `SequentialWorkflow` 改成 `ConcurrentWorkflow`，两个智能体就会同时运行。通过这种方式可选的具名架构有 15 种以上：`MixtureOfAgents`、`GroupChat`、`HierarchicalSwarm`、`MajorityVoting`、`CouncilAsAJudge`、`HeavySwarm`、`DebateWithJudge`、`MultiAgentRouter`、`AgentRearrange`、`LLMCouncil`、`RoundRobin`、`PlannerWorkerSwarm`、`BatchedGridWorkflow`，以及让平台自行选择的 `auto`。改变拓扑是改一个词，而不是一次重构。关于每种形态适用的场景，可以看[智能体编排模式](/zh/blog/agent-orchestration-patterns)。

**两家供应商，一把密钥。** 研究员跑在 Claude 上，分析师跑在 GPT 上。单把 API 密钥背后是 1,605 个模型，覆盖 Anthropic、OpenAI、Google、xAI、DeepSeek、Meta、Moonshot 和 OpenRouter。不需要六个供应商账户，不需要六套计费关系，也不需要琢磨六套限流规则。

**`fallback_model_name` 是按智能体设置的。** 如果主模型报错，该智能体会在回退模型上重试。它是按智能体而不是全局生效的，因此你那个便宜的摘要智能体和那个昂贵的终审智能体可以有不同的降级方式。这是你原本需要自己编写并维护的故障转移能力。

## 定价，也就是大家常忘的那部分

Swarms 按每百万输入 token 6.50 美元、每百万输出 token 18.50 美元计费，而且无论哪家供应商的哪个模型，价格完全相同。把便宜模型换成前沿模型并不会改变你的单位 token 成本，因此模型选择变成了质量决策，而不是预算谈判。平台还有夜间折扣，订阅买到的是访问权限和吞吐能力，而不是更便宜的 token。新账户注册即可获得免费额度。

## 你不必自己搭建的可观测性

每一次运行都会落在 [cloud.swarms.world](https://cloud.swarms.world) 的控制台里。打开任意一次调用，就能看到完整的请求负载、每个智能体的输出，以及这次运行的花费。当某个智能体在生产环境里出问题时，你要问的永远是"我们到底发了什么给它"，而答案已经在页面上了。详见[调用日志](/zh/blog/completion-logs-swarms-cloud)。

## 并排对比

| | CrewAI | Swarms |
|---|---|---|
| 公开基准测试 | 无 | 系统论文、开放测试工具、7.0 倍几何平均、峰值 62.5 倍 |
| 执行模型 | 每次运行在你的进程里重新推导顺序 | 一次编译，作为托管服务运行 |
| 可用模型 | 你自己的供应商账户 | 1,605 个模型，一把密钥 |
| Token 定价 | 各供应商各模型各自报价 | 统一价，所有模型一致 |
| 编排形态 | 顺序与层级两种流程 | 15+ 种，由一个字段选择 |
| 模型故障转移 | 自己写 | 每个智能体的 `fallback_model_name` |
| 可观测性 | 你埋什么就有什么 | 每次运行的完整负载、输出与成本 |
| 需要运维的基础设施 | 进程、队列、工作节点、重试 | 无 |
| 客户端语言 | Python | Python、TypeScript、Go、Java、C#、纯 HTTP |

## 结论

选 Swarms。性能工作是公开且可复现的，而不是单方面声称；架构是一次编译而不是每次运行重新推导；编排跑在别人的基础设施上；而拓扑、故障转移、计费和可观测性，这些你原本要自己搭的东西，在这里只是负载里的字段。

诚实的检验方法是：把一个能跑的 crew 迁过来，数一数你的代码里有多少是智能体本身，又有多少是围绕它们的管道。大多数团队会发现管道占了大头，而这部分在迁移后全部消失。
